## 2026-07-26 — merged the Payload CMS stack into the site

- **Done:** merged PRs #2/#3/#4 (`feat/cms-layout`, which contains the other two) into `main` on top of the finished public site. 12 conflicts resolved by hand.
- **Decisions:** **pnpm is now the package manager** (user's call — `docs/stack.md` had this flagged as an open question); `package-lock.json` removed so only `pnpm-lock.yaml` remains. `messages/*.json` merged as a union — all 37 site namespaces kept, the CMS branch's `site`/`nav`/`common` added on top (they don't collide). The three `src/i18n/*` files were functionally identical on both sides, so ours were kept (they use `hasLocale` rather than a manual cast). `next.config.ts` keeps the CMS branch's `withPayload(withNextIntl(...))` composition.
- **Two things the merge had to fix, or the site would have broken:**
  1. `images.localPatterns` listed only `/api/media/file/**`. Setting that key at all turns `next/image` into an allowlist, so every photo under `/images/**` would have failed with `next-image-unconfigured-localpatterns`. Both patterns are now listed.
  2. The CMS branch's `proxy.ts` replaced next-intl's middleware without delegating to it, which would have killed locale routing (`localePrefix: "as-needed"` needs the middleware to rewrite `/` → `/pl`). The two are now composed in one default-exported `proxy`: host gating first, then `/admin` 404 on public hosts, `/api` passed through untouched, everything else handed to next-intl.
- **Verified after the merge, and four more things had to be fixed to get there:**
  1. **`pnpm@11.17.0` (what the CMS branch pinned) requires Node ≥ 22.13; this project is documented as, and running, Node 20.9.0** — pnpm refused to start at all. Pinned `packageManager` to `pnpm@10.34.5` instead, which supports Node ≥18.12 and reads the same `lockfileVersion: '9.0'`. Added an `engines.node` field so the floor is explicit. **The team is split here:** the PR author is evidently on Node 22. Either raise the project's Node floor or stay on pnpm 10 — but decide it, don't let the two drift.
  2. **`sharp@0.35.3` broke the build on Node 20.9** (`Unexpected token 'with'` — import attributes). Its declared `engines` claims `>=20.9.0`, so this is sharp's own mismatch, not ours. Pinned to `^0.34.5`, which declares `^20.3.0` and builds. Note `next@16.2.11` also declares `>=20.9.0`, i.e. this project sits exactly on the supported floor — expect more of this.
  3. **`graphql@17.0.2` violated Payload's peer range** (`^16.8.1`). Pinned to `^16.8.1`.
  4. **The CMS branch's admin components failed `pnpm lint`** — 4 errors in `AdminNav.tsx` and `PagesTree.tsx`, the same React Compiler rules that caught `PromoBar` earlier. `AdminNav` now reads its localStorage state through `useSyncExternalStore`, and its second effect was deleted outright as redundant (the render already falls back to "open if it holds the active route"). `PagesTree`'s fetch moved behind an `await` with a cancellation flag, which also closes a real unmount race.
- **Verified working:** `pnpm build` and `pnpm lint` clean; `/` Polish and `/en` English (so the composed proxy still does locale routing); `/_next/image?url=%2Fimages/…` returns 200 (the `localPatterns` fix); `/admin` 404s on the public host while `dash.localhost:3000` rewrites to the panel; `/api/users/me` returns JSON. The 22 site routes plus `/admin`, `/api/[...slug]` and both GraphQL routes all build.
- **Watch out:** the create-first-user form **defaults the Role field to `Klient`**, which is precisely the role blocked from the admin panel — accept the default and you get an account that cannot log in. Pick `Administrator`. Also: port 5432 was already taken on this machine by another project's Postgres, so `docker-compose.yml` now takes `POSTGRES_PORT` (default 5432) and binds to `127.0.0.1` instead of all interfaces, which also closes the exposure noted in the review. Also note the CMS branch exported its proxy as a *named* `proxy`, while ours used a default export; the merged file uses the default export, which is the form confirmed working on this project. If the named form is also valid in Next 16, nothing is lost either way. Code style differs across the seam (the CMS files use single quotes and no semicolons, the site files use double quotes and semicolons) — worth one decision and a formatter rather than letting it drift.

## 2026-07-27 — the blog: media sizing, authors, categories, and 62 posts imported

- **Done:** the whole blog. Media finally does what it claimed, `Authors`/`Categories` collections exist, the listing and post template are built, and all **62 articles are in the database** with bodies, inline images, authors, dates, reading times and categories.
- **Media had neither of the two things it advertised.** `imageSizes` was empty, so Payload served the original file for every use. And the WebP hook had a real bug: it returned early for files that were *already* WebP, so an oversized `.webp` passed through with no conversion **and no resize** — and there was no `resize` call at all. Now: originals are capped at a 2560px long edge (aspect preserved, downscale-only) and four sizes are generated (thumbnail 400 / card 768 / content 1200 / hero 1920), all WebP.
- **Authors are not `Users`.** The source has 24 credited names, of which 18 have a portrait. They're trainers, not people who need a CMS login, so `Authors` is its own collection with an optional `user` link for the few who will actually write in the panel.
- **The import** (`scripts/import-blog.ts`, idempotent by slug, `--limit`/`--force`): uses Payload's official `convertHTMLToLexical` plus the Local API. Approved dependency: **jsdom**, dev-only, **pinned to `^26`** — jsdom 30 pulls an ESM-only transitive dep that Payload's tsx runner `require()`s and dies on with `ERR_REQUIRE_ESM`. Images are uploaded first so the Lexical tree can carry real `upload` nodes (`version: 3`); HTML runs between images are converted and spliced around them.
- **Four bugs the verification caught, each of which had silently eaten content:**
  1. **Author portraits all missing.** I derived the author folder from the first 9-char hash in the URL, but that regex matches the *image* hash — the folder is the path segment after `_autors`. Every one of the 18 portraits was being looked up in a directory that didn't exist.
  2. **Junk author roles** like `"& Jakub Grzęda"` and half a sentence, from regexing the concatenated meta text. The card actually has three clean leaf elements — `AUTOR:`, name, role — so it's read structurally now. Anchoring on the **label** rather than the photo also recovered the 14 posts that credit an author without a portrait.
  3. **`north-pole-marathon` lost its entire body.** On that one post the `AUTOR:` label sits inside a wrapper that also holds the article, so removing "the author card" deleted the post. Now guarded by length: a real card is a name plus a job title, so anything over 400 characters isn't one.
  4. **Six posts lost every image** because their `<picture>` leaves the `<img src>` empty and only the `<source srcset>` has the file — the same scrape quirk already on record for the homepage hero video. Falls back to the srcset now.
- **A figure I published earlier was wrong, and I've corrected it in `migration-tracker.md`:** "60 of 61 posts carry content images, 194 in total" counted the author portrait as a content image. The truth is **56 of 62 have content images and 6 have none at all**.
- **Payload's media URLs are absolute and point at the dashboard host** (`serverURL` is the dash URL so the admin links work). That is unusable on the public site: `next/image` rejects the unconfigured host outright — `/blog` 500'd on the first render with real data — and in production visitors can't reach that domain anyway. `src/lib/media.ts` strips the origin, which also makes the path match the `/api/media/file/**` entry in `images.localPatterns`. Inline article images needed the same treatment via a custom `upload` JSX converter in `PostBody`.
- **Watch out:** jsdom prints "Could not parse CSS stylesheet" for these pages — noise from the page-builder's malformed CSS, not a data problem; our own parsing passes a `VirtualConsole` to silence it, but `convertHTMLToLexical` builds its own JSDOM so some noise remains. Post **content stays Polish** — 62 articles is a human translation job. And `readingMinutes` is imported from the source rather than computed, so the `beforeChange` hook only fills it for posts written from scratch.
