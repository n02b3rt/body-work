## 2026-07-25 — menu open/close animations (mobile drawer + desktop mega-menu)

- **Done:** both panels previously did `if (!open) return null`, so nothing could ever transition — an unmounted element has no "from" state. Kept both mounted and drove them off state instead: the mobile drawer slides in from the right (`translate-x-full` → `0`, 500ms) with its rows fanning in on staggered `transition-delay`s, and the desktop mega-menu fades and slides down with its logo mark and five columns rising in sequence. Closing runs with zero delay on every element so dismissing feels immediate instead of sluggish. Added the hamburger→cross morph (middle rule fades, outer two travel to centre and rotate ±45°) rather than swapping two icons instantly. Also added Escape-to-close and body scroll lock while open.
- **Decisions:** first cut animated the mega-menu's `max-height` from 0 to `calc(100vh-65px)`; replaced it with fade+slide because the panel's real height is content-driven (~600px) while the tween target is ~935px, so the reveal would visibly finish around 60% through the duration and the rest would read as mistimed. For scroll lock, used `scrollbar-gutter: stable` on `html` instead of JS scrollbar-width compensation: plain `overflow: hidden` removes the scrollbar, widens the viewport, and shifts the `fixed` header plus all centred content — and a `padding-right` fix on `body` wouldn't correct the fixed header anyway. All animated elements carry `motion-reduce:transition-none`.
- **Watch out:** keeping a closed panel mounted means it's still in the a11y tree and focus order, so both panels get `inert={!open}` **and** `aria-hidden={!open}` plus `pointer-events-none`. `inert` is a genuine footgun here: it's an HTML *boolean* attribute, so `inert="false"` would still disable the panel permanently — it only works because React 19 (19.2.4 here) omits the attribute for `inert={false}`. On React 18 this same code would silently render `inert="true"` as a string and leave the menu unclickable forever. Verified after building that every animation utility actually compiled (transition-property, both durations, the transforms, and the `prefers-reduced-motion` block).

## 2026-07-25 — header responsiveness: found the two real breakpoints (1060 + 1340)

- **Done:** user reported the mega-menu's IG/FB circles squashing into ovals, the close `×` being small/thick/off-centre, the hamburger missing its flanking rules, and asked for the header's responsiveness to be tested properly; plus (mid-task) equal-width footer buttons, bigger partner logos and bigger header social icons. Fixed all of them against measured source values rather than by eye: the circles were squashing because they had no `shrink-0` while a wrapping "MAPA DOJAZDU" button competed for width in a narrow grid column; the `×` was the `&times;` glyph (never optically centred in its em box) — replaced with a stroked SVG; added `border-x` to the hamburger cell. Partner logos were 48×128 where the reference's own `.partner-logo` rule says **180×96 with a 48px gap** and paces the marquee at 3s/logo (→21s for 7), and header social icons were 16–20px where the reference's markup says **28px**.
- **Decisions / the real find:** while checking responsiveness I calculated that the eight nav labels need ~850px, so the nav could not possibly fit at the 1060px breakpoint I'd assumed — it would overflow through the whole 1060–1340px band. Went looking for the reference's actual breakpoints by locating which `@media` block each class prefix's rules live in, and found it uses **two different switches**: `ho:`/`ul:` at **1060px** (type scale, header row 2, desktop-vs-floating Akademia button) and `ug:`/`eo:` at **1340px** (full nav row vs. hamburger-only), plus `xo:` at 1480px for roomier nav padding. I'd collapsed all of that onto Tailwind's `lg` (1024px). Now encoded as `--breakpoint-nav: 1340px` + `--breakpoint-wide: 1060px` with an inline `min-[1480px]:` for the padding step, and documented as a table in `docs/scraped-site-map.md`. Also removed the inter-item gap in the nav and tightened link padding to `px-2` below 1480px (matching the reference's `ph2`→`ph3` step), which is what makes the row actually fit at the 1340px switch point.
- **Watch out:** the nav and the drawer/mega-menu **must** switch on the same breakpoint (`nav:`), or in the gap between two different values you get both panels or neither. Verified after building that both custom breakpoints and every `nav:`/`wide:` utility really compiled (`min-width:1340px` / `min-width:1060px` present, no stale `1024px` header rules) — a mistyped `--breakpoint-*` name generates nothing and fails silently, same trap as the `--text-*` tokens. Traced all five viewport bands (<640, 640–1060, 1060–1340, 1340–1480, ≥1480) for overlap/overflow, including that the floating Akademia pill and row 2's Akademia button never show simultaneously. Note `min-w-60` compiles to `calc(var(--spacing) * 60)`, so grepping the built CSS for `min-width:15rem` gives a false negative.

## 2026-07-25 — full audit against the reference: real type scale extracted and applied

- **Done:** user asked for a full verification pass against the live site. Chrome still unconnected, so instead of eyeballing screenshots I extracted the reference's **actual type scale** out of `assets/css/auto.css` and rebuilt our typography on it. Key discovery — the crucial trick is that the page-builder's breakpoint-prefixed classes (`ho:f12s5`, `ul:f7s4`) live inside media queries, so grepping the bare name (`f12s5`) returns nothing and makes it look undefined; grep the prefixed form. That unlocked the whole scale, now encoded as 14 `--text-*` tokens in `globals.css` and documented as a table in `docs/scraped-site-map.md`. Three systematic errors this exposed, all of which had been wrong since the first session: (1) **headings are font-weight 400, not semibold** — they carry no `fw*` class so they inherit Circular Pro Book regular; every heading on our build was `font-semibold`, i.e. visibly heavier than the real site; (2) **headings have no letter-spacing** — their markup has `ls-0.025em` but that class is *not defined* anywhere in the stylesheet, so it's a no-op, and our `tracking-tight` was inventing tightening that doesn't exist; (3) **the scale is far more uniform than it looks** — nearly every section heading is the same `f12s5` (~68px desktop / ~40px mobile), where we had ad-hoc Tailwind tiers ranging from `text-xl` (20px) to `text-8xl` (96px). Concretely: hero was 96px (real: 68px — the user had already complained it was too big), service tile headings were 20px (real: ~40px, a 2× error), the opening statement's body copy is deliberately huge at ~40px (`f7s6`) which is why the user kept asking for it "bigger", and all body copy everywhere is one single size (`f3.125s3`, ~17.6px). Also rebuilt testimonial cards to the reference's actual structure (hairline `border-r`/`border-b` cards, centered, serif quote glyph on top, attribution at bottom in 12.7px/weight-300/1px-tracking) and added the navy-circle prev/next arrows as a shared `CarouselArrows` component; pinned the Zespół column's heading to the top and copy to the bottom (`textLayout="split"`) with the photo now stretching the full row height; widened the "Przyjazna przestrzeń" card to `max-w-4xl` since at the heading's real 68px it needs ~800px to stay on one line (it was wrapping to two); added the BODYWORK zigzag mark to the partners block.
- **Decisions:** put the scale in `globals.css` as `@theme` tokens rather than repeating arbitrary values (`text-[1.1019rem]`) at call sites — one source of truth, each token commented with the reference class name it came from so any value is re-verifiable. Kept `text-h-display` as `clamp(3.5rem, 17vw, 17.6305rem)` rather than the reference's JS-fit-to-container approach: same visual result on a normal desktop, but it stops growing on ultrawide, which is the standing width constraint for this project.
- **Watch out:** **verify that new `@theme` tokens actually compile** — a typo'd token name produces no CSS and fails silently. I checked all 15 against the built stylesheet; note the build minifies leading zeros (`0.7934rem` → `.7934rem`), so a naive grep for the authored value reports a false "missing". Two `text-2xl` remain in `Header`/`MobileNav` on the `×` close glyph — decorative icon sizing, deliberately outside the scale. `NewsCarousel`'s cards still don't match the reference (no images, no "WIĘCEJ" button, no arrows) — that's deliberate, the user explicitly deferred it until the blog exists and asked for the heading only.

## 2026-07-25 — PhotoTextCard: fix card spilling below the photo

- **Done:** the previous round's `PhotoTextCard` fix (anchoring with padding instead of `Container`) was necessary but not sufficient — a follow-up screenshot showed the card's heading sitting correctly on the photo, but the body paragraph and button spilling out *below* the photo entirely, where they lost all contrast (invisible-looking, since the card and the page background are both the same cream). Root cause: the card was pulled up into the photo with a *guessed* fixed negative margin (`sm:-mt-24 lg:-mt-32`) from normal document flow — that guess is only as tall as it is, and a card with a full paragraph of body copy is taller than the guess, so everything past that height overflowed past the photo's bottom edge onto the plain page. Fixed properly this time: the card is `absolute`, anchored to `bottom-0` of the (`relative`) photo container, so it structurally cannot overflow below the photo — it can only grow upward into it, regardless of text length, locale, or viewport width.
- **Watch out:** this is the second time a "pull a floating element up with a negative margin sized by eyeballing" approach broke — first the header flip/collapse (fixed by switching `sticky`→`fixed` + a spacer), now this card (fixed by switching negative-margin→`absolute`+anchor edge). **General lesson: don't use a guessed fixed negative margin to overlap a content-driven-height element onto a fixed-height sibling — anchor it with `absolute` positioning against an edge instead, so containment is structural, not a magic number.** Still unverified live — user is testing directly and reporting screenshots, which is now the primary QA loop for this project in place of Claude-in-Chrome.
