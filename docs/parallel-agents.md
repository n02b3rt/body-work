# Working in parallel: several agents, one repo

Three coding agents (different tools, different terminals) can share this repo, but
only if each one gets its **own working tree, its own database and its own port**.
The hard part is not git, it is the local state Payload keeps outside git: the dev
schema push, the uploads on disk, the generated types.

Read this before starting work if anyone else is working on the repo at the same
time. If you are the only agent running, skip to "Files that always conflict",
which still applies to any long-lived branch.

## 1. One worktree per agent

```bash
git worktree add ../bw-a -b feat/a-<topic>
git worktree add ../bw-b -b feat/b-<topic>
git worktree add ../bw-c -b feat/c-<topic>
```

One `.git`, three independent checkouts. Git refuses to check out a branch that
another worktree already holds, so no agent can pull the rug from under another.
`pnpm install` in each: pnpm hardlinks from the shared store, so the disk cost is
small.

Branch names carry the agent's letter (`feat/a-…`, `fix/b-…`) so a PR list is
readable at a glance. The prefix rules from `docs/conventions.md` still apply.

**Nothing gitignored is shared between worktrees.** Each new worktree needs its
own `.env` (copy `.env.example`), and gets its own empty `media/`, `.data/`,
`.next/` and `node_modules/`.

## 2. One database and one port per agent

This is the part that actually breaks things. Payload runs the dev schema in
**push mode**: it alters tables to match the config on startup. Two agents editing
`src/collections/` or `src/fields/` against the same database will overwrite each
other's schema, and one `docker compose down -v` wipes the other two agents' data.

Three databases inside the one dev container is enough — no second container:

```bash
docker compose up -d
docker compose exec postgres psql -U payload -d bodywork -c 'CREATE DATABASE bodywork_a;'
docker compose exec postgres psql -U payload -d bodywork -c 'CREATE DATABASE bodywork_b;'
docker compose exec postgres psql -U payload -d bodywork -c 'CREATE DATABASE bodywork_c;'
```

Then in each worktree's `.env` (note the variable is `DATABASE_URL`, and every URL
has to agree on the port):

```
DATABASE_URL=postgresql://payload:payload@localhost:5432/bodywork_a
NEXT_PUBLIC_SERVER_URL=http://localhost:3001
NEXT_PUBLIC_DASHBOARD_URL=http://dash.localhost:3001
```

Start with `pnpm dev --port 3001` (3002, 3003). `DASHBOARD_HOST` stays
`dash.localhost`; the host proxy matches on hostname, not port.

**Port and `.env` must agree.** Payload CSRF only accepts the auth cookie on
POSTs whose `Origin` matches `NEXT_PUBLIC_DASHBOARD_URL` (and a small allowlist
of common agent ports in dev). If you open `http://dash.localhost:3000` while
`.env` says `:3003`, the admin UI can still look logged in (GETs skip Origin),
but saving media or editing docs fails with *"Nie możesz wykonać tej akcji"* /
`UnauthorizedError` on form-state. Fix: restart with the port from `.env`, or
update the three URL lines to match the port you actually use.

Each database needs its own first admin user, and uploads live in that worktree's
own `media/` folder, so a Media document created in one worktree is not resolvable
in another. That is the point: it keeps a destructive reset local to one agent.

**Never run `docker compose down -v` while another agent is working.** It destroys
the shared volume, which means all three databases.

## 3. Split ownership by module, not by file

The project map in `CLAUDE.md` is the cut. A workable split:

| Agent | Owns |
|---|---|
| A | admin panel and builder: `src/components/admin/`, `src/fields/`, `src/globals/` |
| B | public site: `src/app/[locale]/`, `src/components/centrum/`, `src/components/elements/`, `messages/` |
| C | API, collections, scripts: `src/app/api/`, `src/collections/`, `scripts/`, `src/lib/` |

The rule is hard: **an agent does not edit files outside its area.** If it needs a
change next door, it reports the need instead of making it. This removes most
conflicts before they exist.

## 4. Files that always conflict

| File | Why | What to do |
|---|---|---|
| `src/payload-types.ts` | generated; changes on every field edit | don't merge it — after each merge into `main` run `pnpm generate:types` and commit the result on its own |
| `src/app/(payload)/admin/importMap.js` | generated by `pnpm generate:importmap` | same |
| `pnpm-lock.yaml` | only one agent may install anything | covered by the "ask before touching the stack" rule |
| `docs/log.md` | everyone prepends a line | write the entry when the branch merges, not while it lives |
| `CLAUDE.md`, `docs/*.md` | everyone appends a table row | plain text conflict, resolve by hand |
| `messages/pl.json`, `messages/en.json` | two agents append keys in the same place | split by namespace; conflicts stay trivial |

A `.gitattributes` with `merge=ours` on the two generated files silences the merge
noise, but regeneration after the merge remains the source of truth.

## 5. Merge one at a time, rebase immediately

One PR lands in `main` at a time. **Every other worktree rebases onto `main` right
after** — not tomorrow. A conflict across 3 files after an hour is solvable; the
same conflict across 40 files after three days is not.

So: one feature per PR, branches measured in hours. This matters more than
everything above it.

## 6. What cannot be parallelised

- **Payload schema changes** — collections, fields, `dbName`. One agent, one
  session. Two concurrent PRs touching `src/collections/` produce a schema nobody
  can reconstruct.
- **Stack changes** — they need the user's approval anyway.
- **Cross-cutting refactors** that touch dozens of files. Do them solo, merge, then
  fan out again.
- **`pnpm build`** reserves a 4 GB heap (see `package.json`). Three at once will
  swap the machine; run builds one at a time.

## 7. The two runbooks, one per tool

Two procedures carry this workflow:

| Runbook | When | What it does |
|---|---|---|
| `docs/runbooks/start-parallel-work.md` | before starting a task next to another agent | picks a free slot (worktree, branch off `origin/main`, database, port), copies and patches `.env`, installs, writes `.agent-scope` |
| `docs/runbooks/post-merge-sync.md` | right after any PR lands in `main` | rebases this worktree, regenerates the types and import map, pushes the schema to **this slot's** database, verifies |

A slot is a sandbox, not a specialisation: `start-parallel-work` deliberately does
not tie slot `a` to any folder. The scope comes from the task the agent was given
and is recorded in `.agent-scope` (excluded via `.git/info/exclude`), so the other
agents can see what is taken.

**The runbooks are the only copy of the procedure.** Each tool gets a pointer, never
a paraphrase, so the three agents cannot drift apart:

| Tool | Adapter | Invoked as |
|---|---|---|
| Claude Code | `.claude/skills/<name>/SKILL.md` | model-invoked, or `/<name>` |
| Cursor | `.cursor/commands/<name>.md` | `/<name>` |
| Cursor (always-on guardrails) | `.cursor/rules/parallel-agents.mdc` | automatic |
| anything else (Grok CLI, …) | `prompts/parallel-agent-bootstrap.md` | paste, or point the tool's own instruction file at the runbook |

Adding a tool means adding a pointer file, not another copy of the steps. If you
find yourself editing the same instruction twice, the split has been broken —
fix it back.

## 8. Same rules for every tool

`AGENTS.md` points every non-Claude agent at `CLAUDE.md`. Tools without skill
support run sections 1–6 by hand — the steps are the same. Tools that only read one
file need this page's essentials pasted into their system prompt: branch prefix
with the agent's letter, never edit generated files, never `docker compose down
-v`, never commit to `main`.
