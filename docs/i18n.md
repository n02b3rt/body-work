# i18n — Polish / English

> Every page and component ships bilingual from the start. Written in English. Full requirement: PRD.md §8.10.

## Two layers — don't mix them

BODYWORK content splits into two kinds of text, translated two different ways:

1. **UI/interface strings** (buttons, labels, nav, form errors, static chrome) → **next-intl**. Lives in message files, not hardcoded in components.
2. **CMS content** (page copy, blog posts, course descriptions — anything an editor writes in Payload) → **Payload's field-level localization** (`localized: true` on the field). PL is the default locale, EN is optional per field.

Don't put translatable UI copy in Payload, and don't put page content in next-intl message files.

## Routing

- `/...` → Polish (default, no prefix)
- `/en/...` → English
- `hreflang` + `x-default` set on every page, pointing at the PL version.

## Fallback rule

If a piece of CMS content has no EN translation, **the page does not appear in EN** — no half-translated skeleton. It can still show in list views with a fallback to PL (PRD §8.10). Don't build a "PL text shown on the EN page" fallback for content pages — that's worse than not showing them at all.

## Current state — read before translating anything

The scraped Centrum mirror (`scripts/scrape/scraped/`) is **Polish-only**. The live `bodywork.testowe.eu` reference site has no English version, even though PRD §4 requires one for the finished Centrum ("✅ Wersja EN"). Consequences:

- There is no English source text to copy for Centrum pages — it has to be translated from the Polish scraped content as each page is built, not lifted from a reference.
- Every new Centrum page/component must still be wired up for next-intl / localized fields from day one, even though only the PL copy exists right now. Don't ship a structurally PL-only page and bolt on i18n later.
- Track per-page/template EN translation status in [`migration-tracker.md`](./migration-tracker.md).

Akademia has no reference content at all yet (no design delivered) — build it bilingual from its first page; there's no PL-only legacy to retrofit there.

## Gotchas

- qTranslate-X artifacts (`[:pl]...[:en]...`) show up in the *old WordPress* export, relevant only to the future WP → Payload migration scripts (PRD §8.10, §15) — not something you'll see in the scraper mirror, which is a different, newer reference site.
- next-intl is installed and wired up (`src/i18n/`, `src/proxy.ts`, `messages/{pl,en}.json`, `src/app/[locale]/`). Structured list content (news items, testimonials) is stored as JSON arrays in the messages files and read with `t.raw("items")` — ICU message functions are for strings, not arrays/objects.
- Locale switching preserves the current page: use next-intl's `Link` from `@/i18n/navigation` with an explicit `locale` prop (see `Header.tsx`), not a hardcoded `/en/...` href.
